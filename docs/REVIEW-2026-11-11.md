## 4. Naming options

**A) Metadata only (low risk).** Change what does not touch the bench app name:
root `package.json` (name `paypilotlabs-erp`, repository/homepage/bugs → PayPilotLabs, author kept),
`banking/package.json` name, pyproject `[project.urls]` and `description`, add `maintainers = PayPilotLabs`,
`hooks.source_link`. About 5 files. The Python package, `app_name`, `/assets/erpnext/` paths and
`--install-app erpnext` stay. Users never see "erpnext" except in asset URLs and the API method paths.

**B) Full rename to `paypilotlabs_erp` (high risk).** Move `erpnext/` → `paypilotlabs_erp/`; rewrite
~8,700 `erpnext.` references in 1,247 files (imports, `frappe.call` method strings, hooks dotted paths,
`patches.txt`, `"app": "erpnext"` in 66 JSON records, `/assets/erpnext/` in 28 places, Vite base, pyproject
`[tool.bench.assets]`, `[project] name`, `app_name`, CI, independence check, compose `--install-app`), plus
`frappe.provide("erpnext.…")` JS namespaces (cosmetic but touched by the regex), a migration patch for
existing sites, and updates in paypilotlabs-hrms. Every downstream merge from upstream erpnext becomes a
conflict on nearly every file. Third-party apps written for ERPNext (they import `erpnext`) stop working.

**Recommendation: A.** Nobody outside the code sees the package name; B buys nothing a customer notices,
breaks hrms and every ERPNext-compatible app, and makes upstream security fixes very hard to pull.
